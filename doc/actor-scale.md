# Actor scale — what a run carries, per actor kind, and what stops it

**Why this file is outside the mirror.** Its subject is a CAPACITY, and no single source directory owns
one: the number is set by `missions/FBMissionRunner`'s phase order, `missions/FBTickPool`, the six
registry readers in `sensors/` + `modules/`, `core/FBMissionMonitor`'s roster pass, `units/FBSimUnit`'s
`PublishPose` + telemetry and `clients/`' one file per actor — five layers at once. It sits beside
[`doctrine-evolution.md`](doctrine-evolution.md), outside the mirror for the same reason (a MEASUREMENT,
not a module). [`missions/runtime.md`](missions/runtime.md) §9 keeps the 2–4 unit thread-pool numbers;
this file extends them and replaces none.

**The question this file answers, in the form the owner set it.** The gym runs *scenarios with thousands
of actors*, but *hardly more than a few dozen modules will be online at once*. So the expensive class is
capped BY DESIGN, not by a limit, and the measurement that matters is the MIXTURE: two dozen modules
plus N cheap actors — positions, targets, rounds in the air, kinematic movers. What does each kind cost,
how far does N go, and does the quadratic in the six registry readers run over the cheap actors too.

---

## Spec

| Contract | Acceptance / measurement anchor |
|---|---|
| The cost of one actor is known per KIND, separately, so a scenario can be estimated on paper | `tools/fb_scale_bench.py` profiles: `bare_*` (a kind alone), `mix_*` (24 modules + N of one kind), `mix_theatre` (24 modules + a realistic mixture), plus the pure-fighter chain `blind`→`quiet`→`fcr`→`fcrdl`→`sensors` |
| The quadratic term is attributed to a NAMED reader, and it is known whether it runs over the cheap class | matched delta `mix_X − mix_none − bare_X`, divided by N and by the observer count |
| Determinism does not depend on cast size, mixture or thread count | SHA-256 over all `telemetry*.csv` + normalised `events.log` + exit code identical over `--threads 1/2/4` **at every measured point** (`tools/fb_campaign_verify.py::mission_fingerprint`, reused verbatim) |
| The cheap class's ceiling is stated with WHAT breaks first | wall clock, RSS, trace bytes, telemetry file count and the fixed-size tables recorded per run |
| No actor is ever computed differently because of where it is | source verdict, §8 — and the fingerprint gate is the instrument that would catch a violation |

## State

Measured 2026-07-29 against the committed `sim/build/fb-gym` (linked 2026-07-29 11:08, newer than every
file under `sim/src/`). **Nothing was rebuilt and no simulator source was touched.**

**Host.** Apple A18 Pro — 6 logical cores = **2 performance + 4 efficiency** (`sysctl
hw.perflevel0.logicalcpu` = 2, `hw.perflevel1.logicalcpu` = 4), **8 GiB RAM**, 4 GiB swap, 1.73 GB/s
disk (`dd bs=1m count=1200`), macOS 26.4.1, arm64, `ulimit -n` = 1 048 576. A 2P+4E machine is not four
equal cores, so every `--threads 4` figure is against THIS machine.

**Command**, every point:

```
build/fb-gym --mission missions/scale/<profile>-<n>.fbm --out DIR --elev const --threads T
```

from `sim/`, wrapped in `/usr/bin/time -l` for peak RSS. The measured quantity is the runner's own
`wallS` from the `mission SUMMARY` line — `steady_clock` over the tick loop only, so JSBSim model
loading and process start sit outside it (reported separately as `procS`). `--elev const` by decision:
the baked DEM is an I/O path whose cost is not the cast's.

**Missions.** Generated by `sim/tools/fb_scale_bench.py` into `mods/f16/src/missions/scale/` — a new directory,
deliberately outside the regression glob `mods/f16/src/missions/*.fbm`. Common cast text: a 0.02° lattice, 32
columns (≈ 1.5 × 2.2 km per cell, so density is constant and the EXTENT grows with N), aircraft at
9 000 m / 450 kt, one waypoint 4° downrange so no plan ever completes, `timeout 30`, no combat
objectives outside `combat`. Every run ends at exit 3 (TIMEOUT) after exactly 30.0 sim-seconds — the
duration is a constant, which is what makes the wall clocks comparable.

**Repetitions.** 3 up to N = 1024, 2 above, 1 at N = 4096. Tables quote the MEAN; the fits use the MIN,
the less contaminated estimator for a CPU-bound run. **The spread is not uniform**: the mixed and cheap
casts came in under 1 % (`bare_target` sd ≤ 0.4 %), the large pure-fighter casts throttle — worst case
`blind` N = 2048 `--threads 1` gave 126.9 s and 161.8 s back to back (sd 17 %). Points with sd > 5 % are
marked `~`.

### 2. Cost per actor KIND — the table to estimate a scenario with

µs of wall clock per sim-second per actor of that kind, `--threads 1` unless noted. "alone" is the
`bare_*` profile (nothing in the run looks at it); "beside 24 modules" is `mix_* − mix_none`, divided by
N. Three cast sizes are given because two of the four kinds grow with N and two do not.

| kind | module key | alone, N=64 / 256 / 1024 | beside 24 modules, N=64 / 256 / 1024 | t=4, N=1024 | grows with N? |
|---|---|---:|---:|---:|---|
| **inert ground target** | `target_soft` `target_hard` | 176 / 173 / 176 (and 189 at N=4096) | 259 / 203 / 192 (200 at 4096) | 188 | **no** — flat to 4096 |
| **kinematic air mover** | `an26` (any `FdmModel`-less catalogue row) | 191 / 212 / 284 | 280 / 243 / 305 | 245 | +0.09 µs per peer |
| **air-defence position** | `sa2` `sa3` `sa6` `sa8` `zsu23` `p18` | 380 / 632 / 1195 † | 379 / 512 / 1221 | 662 | **+0.79–0.92 µs per peer** |
| **round in the air** | `aim120` | 980 / 1051 / 1656 ‡ | 1065 / 1034 / 1049 | 608 | no (its uplink breaks on the launcher id) |
| **fighter, boxes on** | `f16` `mig29` | 1545 / 1759 / 2553 | — (it IS the base load) | 1293 | **+0.70 µs per peer** |
| **fighter, boxes off** | `f16` with FCR/DL/RWR/eye off | 1313 / 1474 / 1593 | — | 836 | no (§5) |

† the `ground` profile is N positions **plus one blind F-16 probe**, so its N = 64 column carries ~20 µs
of that probe amortised; from N = 256 on the contamination is under 1 %. ‡ the `missile` profile's means
were 12–18 % noisy at N ≥ 128, so its "alone" column quotes the MIN; every other cell is the mean.

| kind | RSS per actor | trace per actor per sim-second | parallelises? |
|---|---:|---:|---|
| inert ground target | **0.051 MB** | 9.71 KB | **no** — 176 µs at 1, 2 and 4 threads alike |
| kinematic air mover | 0.055 MB | 10.13 KB | weakly, 1.2× |
| air-defence position | 0.090 MB | 10.32 KB | yes, 1.85× at N=1024 |
| round in the air | 0.289 MB | 10.66 KB | yes, 1.72× |
| fighter | 0.511 MB | 10.14 KB | yes, 1.97× |

Four things in that table are worth saying out loud:

1. **An inert target costs ~180 µs per sim-second and NOTHING it does is simulation.**
   `FBGroundModule::Run` is literally empty. The 180 µs is the runner's sequential per-actor work:
   the elevation/wind/sky sample, `PublishPose` (which builds the whole 928-byte `FBUnitSignature`
   even for a unit that publishes nothing), `CheckEnvelope`, `SampleTelemetry` (184 columns) and
   `PrevPose`. That it does not parallelise at all — 176 µs at one thread and at four — is the proof:
   none of it is in the STEP the tick pool distributes.
2. **A round in the air is NOT a small actor.** ~1050 µs, i.e. two thirds of a fighter with its boxes
   off, because `FBMissileModule::Run` integrates the same fixed 100 Hz substeps and writes the same
   184-column trace. *Caveat:* these are `aim120` units DECLARED in the `.fbm`, and `FBMissileModule`
   does not override `FBModule::UnitKind`, so the boot gives them `Aircraft` where a RELEASED store
   gets `Weapon`. Same module, same FDM, same step cost; the kind changes only who may see them.
3. **An air-defence position has no flight model and is still the kind whose cost EXPLODES.** 380 µs at
   N = 64, 1221 µs at N = 1024 — because `FBSiteModule::Run` cycles four registry walkers per tick (ESM,
   search radar, track radar, optics) plus a fifth when netted, and its linear part is small enough that
   the quadratic owns it from **N ≈ 510** (a/b of the fit `402 + 0.787·N`). For a fighter the same
   crossover is at **N ≈ 2680**.
4. **The trace is ~10 KB per actor per sim-second for EVERY kind**, from a bunker to a fighter. The
   schema is effectively fixed-size regardless of what the actor is.

### 4. Do the six registry readers run over the cheap actors? Yes — one of them does, and it is small

The clean experiment: `mix_target − mix_none − bare_target`, per target. An inert target radiates
nothing, is not an `Aircraft`, and can therefore never legitimately appear in any picture — so whatever
this delta is, it is pure waste.

| N targets | t=1 | t=2 | t=4 |
|---:|---:|---:|---:|
| 64 | 82.9 µs | 35.1 | 29.2 |
| 256 | 30.2 µs | 11.1 | 12.4 |
| 1024 | 15.4 µs | 9.5 | 10.0 |
| 4096 | **11.4 µs** | 8.8 | 7.4 |

(the small-N values are the fixed overhead of a 1.4-second run, not a signal; the number converges from
N = 1024 on.)

**11.4 µs per cheap actor per sim-second, for 24 observers = 0.47 µs per observer per cheap actor per
sim-second.** The source says exactly where it comes from and predicts the number:

| reader | filter applied BEFORE any geometry | touches an inert target? |
|---|---|---|
| `FBRadarSystem::ScanFrame` | self, then `GetKind() != Aircraft` | no — skipped on an inline getter |
| `FBIrstSystem::ScanFrame` | self, then `GetKind() != Aircraft` | no |
| `FBVisualSystem::ScanFrame` | self, `GetKind() != Aircraft`, then all-zero visual signature | no |
| `FBDatalinkSystem::Cycle` | team; then `CarryAir_`/`CarryGround_` kind gate | no (a foreign target with `CommJamM` = 0 is dropped before the distance) |
| `FBMissileUplink::Run` | `GetId() != LauncherId_` → break | no |
| **`FBRwrSystem::Run`** | **self, and nothing else** | **YES — it copies the 928-byte `FBUnitSignature` by value and computes `FBEnuOffsetM` + a `sqrt` for every unit in the registry, and only then discovers that every beam is `Mode::None`** |

The RWR sits in the F-16 module's 10 Hz defensive group (`Due(DefensiveAccS, dt, 10.0)`), so it walks
once per tick. Predicted waste: 24 observers × 10 walks/s × ~53 ns per pair = **12.7 µs** against
**11.4 µs** measured — agreement to 10 %.

**And it is 6 % of the target's own 189 µs.** Extrapolated to the owner's case, 1000 non-radiating cheap
actors beside 24 modules waste 11.4 ms per sim-second out of ~870 ms. **A pre-sort by actor kind is
therefore correct, cheap and NOT the lever** — it would buy ~1.3 % of the mixed cast. The lever is what
the other 94 % is (§6, G1).

|---:|---:|---:|---:|---:|---:|---:|

| 64 | 1313 | 703 | 1545 | 792 | 42 | 19.6 |

| 4096 | 1996 | 1098 | 4693 / 11693 (§7) | 3544 | 2079 / 2052 | 1224 / 1264 |

`y = a + b·N`, least squares on the MIN over N ≥ 32, `--threads 1`:

| profile | walkers per actor | a (µs) | b (µs per peer) | a/b |
|---|---|---:|---:|---:|
| `blind` | none | 1372 | 0.192 | 7163 |
| `sensors` | eye (1 Hz) + FCR (0.25 Hz) + datalink (2 walks at 1 Hz) + RWR (10 Hz) | 1461 | 1.063 | 1374 |
| `combat` | as `sensors`, half MiG-29 (adds an IRST), plus two objectives per unit | 1322 | 1.427 | 926 |
| `ground` | ESM + search radar + track radar + optics | 402 | 0.787 | 511 |

**`blind` has a slope although it does no O(N) work per actor.** Nothing in the blind step or in the
runner's sequential passes is O(N) *per actor* — `BuildRoster`, `PrevPose` and the log drain are O(N) per
TICK, i.e. O(1) per actor. That 0.192 µs/peer is the WORKING SET (0.51 MB per F-16 actor: between two
ticks of the same actor every other actor's JSBSim state passes through the caches). So the honest
walker coefficient is the matched difference, which cancels it:

| N | 64 | 128 | 256 | 512 | 1024 | 2048 |
|---|---:|---:|---:|---:|---:|---:|
| `sensors − blind` | 234 | 243 | 272 | 528 | 934 | 1579 |

> **Δ = 158 + 0.704·N.** The four walkers cost **0.70 µs per peer per actor per sim-second** — 53 ns per
> (observer, observed) pair per walk, against a `sizeof(FBUnitSignature)` of **928 bytes** (measured),
> returned BY VALUE inside every one of those loops. Fifteen cache lines per pair per walk.

**Which walker: the RWR, by its cadence, not its arithmetic.** Measured back to back in one session,
N = 1024, `--threads 1`, 3 repetitions each — the chain is five single additions:

| cast | blind | + eye | + FCR | + datalink | + RWR |
|---|---:|---:|---:|---:|---:|
| µs/actor/simS | 1955 | 1938 | 2082 ~ | 1929 | **2703** |

The eye, the FCR and the datalink together are **indistinguishable from `blind`** at this measurement's
resolution (±8 %, and their apparent order is noise). The RWR is not: +774 µs on the same cast, i.e. it
alone is ~0.76 µs/peer of the 0.70 µs/peer total. Its `FrameS` equivalents are the reason —
`FBVisualFieldOfRegard::FrameS` = 1.0 s, `FBDatalinkSystem::kNetPeriodS` = 1.0 s, the F-16 CRM volume's
`FrameS` = 4.0 s, while the RWR runs at the module's 10 Hz slot rate with no frame period of its own.

| quantity | measured | derivation |
|---|---|---|
| process floor | 7–9 MB | RSS at N = 1 |
| RSS per actor | 0.051 (target) · 0.055 (mover) · 0.090 (position) · 0.289 (round) · 0.511 MB (fighter) | §2 |

| of which disk I/O | **3 %** | 1192.8 MB at 1.73 GB/s = 0.69 s of a 23.27 s run — the rest is CPU spent PRODUCING the row |

**The file-descriptor limit is a hard cap on actor count, and it is host configuration.** This host allows
1 048 576, so it never bit. A host left at the macOS default `ulimit -n` = 256 cannot run a cast of more
than ~250 actors at all: the run dies at boot with `RESULT reason="cannot open telemetry.csv"`.

### 7. The one place a measurement fell off its model: memory, at N = 4096 with the boxes on

The CPU model of §5 predicts `sensors` N = 4096 at 1461 + 1.063 × 4096 = 5815 µs. Measured twice at
`--threads 1`:

| run | wall for 30 sim-s | µs/actor/simS | swap in use | process CPU |
|---|---:|---:|---:|---:|
| first (immediately after `blind` N = 4096 had written 1.2 GB of trace) | 1436.8 s | 11 693 | **3.03–3.25 GB of 4 GB**, 68 MB free pages | **56 %** |
| repeat, half an hour later | 576.7 s | 4 693 | 2.67 GB | — |

Same binary, same mission, same 2 GB RSS, **2.5× apart**. The first run was paging, not computing. So on
an 8 GiB host N = 4096 full-sensor fighters sits ON the memory edge — whether a run pages depends on what
else is resident, and it is not a clean cliff. It is also the ONLY point in this whole campaign where a
measurement left its model; every cheap-class and mixed point came in under 2 % spread.

**The cheap class does not parallelise at all** (s ≈ 1.0 for inert targets) because none of its cost is
in the STEP. With s ≈ 0.29–0.49 for everything else, the tick loop cannot be sped up by more than
2.0×–3.4× by threads at any thread count. Everything outside `pool.RunTick` is sequential by
construction: the elevation/wind/sky/solar sample loop, the log drain, `PublishPose`, `BuildRoster`,
`CheckEnvelope` + `RunMonitors` (both judges), `SampleTelemetry`, the gun and store resolution passes,
the hook, the actor-growth phase and `PrevPose`.

### 10. Range-dependent activation: there is none

**A source verdict, categorical rather than a sample.**

| candidate path | what it actually does |
|---|---|
| `FBActorStepJob::RunIndex` | steps actor *i* unconditionally; the one early return is `!Active()` — retirement after a store impacted (`FBSimUnit::Retire`), a simulation fact, not a distance |
| `FBTickPool::RunTick(job, Actors.size())` | every index, every tick; no partitioning, no budget, no priority |
| the six registry readers | §4's table — every pre-geometry filter is an IDENTITY filter (self, kind, team, terminal, launcher id), never a distance |
| the three range tests that do exist (`FBRwrSystem.cpp:101`, `FBRadarSystem.cpp:46`, `FBIrstSystem.cpp:80`) | cull the RESULT after the geometry has been computed, never the work |
| `FBMissionRunner` gun / store passes | `for each of 64 bundles × for each actor` and `for each store in flight × for each actor`, both SEQUENTIAL; guards are kind, self and launcher id |
| `FBMissionMonitor::Tick` | walks the roster once per roster-decidable objective, per judged unit, per tick — sequential |
| telemetry | `SampleTelemetry` for every active actor, every tick, 184 columns, its own file |

There is no spatial index, grid, quadtree, budget or activation radius anywhere below `render/` and
`world/`; the only quadtree in the tree is the terrain streamer's, which draws and does not simulate.
`ActivationRangeM` in `core/FBStore.h` is a seeker's pitbull range — physics, not an optimisation.

One consequence worth naming: a retired store is NOT removed from the registry (removal would move every
later index and tie tick order to when a bomb happened to land). It keeps being iterated by every walker
for the rest of the run, with a zeroed signature. **In a long engagement the N of the N² is the number of
units ever spawned, not the number still alive** — and by §4 the only reader that pays full price for
such a unit is, again, the RWR.

### 11. The limit that is not a compute limit

Every picture in the tree is a fixed table of **8**:

| table | constant | overflow policy |
|---|---|---|
| radar contacts | `kMaxRadarContacts = 8` | `FBRadarSystem.cpp:162` — *"Trackdatei voll; nichts wird verdraengt"* |
| RWR threats | `kMaxRwrThreats = 8` | `FBRwrSystem.cpp:133` — same, nothing displaced |
| datalink tracks | `kMaxDatalinkTracks = 8` | `break` out of the registry walk |
| IRST / visual contacts | `kMaxIrstContacts` / `kMaxVisualContacts = 8` | as the radar |
| flight positions | `kMaxFlightPosition = 8` | a flight cannot exceed eight |
| gun bundles | `FBGunProjectiles::kMaxBundles = 64` | **process-wide, shared by the whole cast**; a 65th burst is dropped with `gun BURST_DROPPED` |
| emitter beams per unit | `kMaxEmitterBeams = 2` | at most two antennas per unit |

Because nothing is displaced, the eight a unit holds are **the first eight eligible peers in mission
declaration order**. Measured on `sensors` N = 2048: `datalink TRACK_GAINED` fires exactly
16 384 = 2048 × 8 times, and the RWR churns 28 281 `THREAT_NEW` against 12 745 `THREAT_DROP` as peers
cross beam windows and free slots refill — 75 579 event lines for one 30-second run.

For the MIXED cast this matters less than it looks: the cheap class is invisible to five of the six
readers by kind, and the expensive class is capped at a few dozen by design. **But above roughly a dozen
mutually visible MODULES, every picture is a declaration-order truncation** — which is the real argument
for the owner's "a few dozen modules" bound, quite apart from cost.

## Gaps

Ordered by what actually limits the gym's mixed cast.

**G1 — the trace, and the ~180 µs of per-actor sequential overhead behind it.** This is the cheap class's
whole cost. An inert target does no simulation at all and still costs 176–189 µs per sim-second, of which
only 3 % is disk I/O (§6) — the rest is CPU spent producing the row and the pose: 184 `snprintf`ed
columns at 10 Hz, plus `FBSimUnit::PublishPose` assembling the full 928-byte `FBUnitSignature`
(8 chaff clouds, 8 flare clouds, 2 beams, flight report, net report) for a unit that publishes nothing.
Volume: 4096 cheap actors emit **143 GB per sim-hour**. Three levers, none of which touches simulation
semantics: a per-unit sample rate, an opt-out (`telemetry off` as a `.fbm` key), and an early-out in
`PublishPose` for a module whose signature is provably constant. **Not isolated:** the 180 µs was not
split between the formatter and `PublishPose`. Next measurement, and it is cheap — the two are separable
by a single cast that declares `telemetry off`.

**G2 — `FBRwrSystem` has no frame period and no pre-geometry filter.** It is the one reader that pays
full price for every unit in the registry regardless of kind (§4) and it is ~75 % of the fighter
quadratic (§5). Two independent fixes, both small: (a) test the published emission before the 928-byte
copy — a `bool Radiating` on `FBUnit`, or hoisting the `Mode == None` check — which is provably
result-identical and removes the waste over the entire cheap class; (b) give the RWR a `FrameS` the way
the radar and the eye have one. **(b) changes what the receiver hears and is a SIMULATION decision for
`doc/sensors.md`, not a performance patch.** Measured prize for (a) in the owner's mixture: ~1.3 %.
Measured prize for (a)+(b) in a pure-fighter cast at N = 1024: up to 30 %.

**G3 — the sequential passes that are worse than O(N).** The store fuze pass is O(stores in flight × N)
and the gun pass is O(64 × N), both single-threaded in the runner. DERIVED, not measured: a 30-second
cast never reaches the merge, so no run in this campaign put stores in the air. Two dozen modules with
two rounds each is only 48 stores, so for the owner's bound this is bounded too — but a theatre where
1024 positions each fire is not. **Unmeasured, and the one place a mixed cast could still surprise.**

**G4 — the file-descriptor cap is host configuration, and a failed `fopen` is fatal.** One `FILE*` per
actor for the whole run; on a host left at the macOS default of 256 the cast dies at boot above ~250
actors (§6). Either the runner tolerates a missing trace for a mission actor the way it already does for
a store (`StartTelemetry(nullptr)`), or `build-and-ops.md` states the required `ulimit -n`.

**G5 — memory for the EXPENSIVE class only.** 0.51 MB per fighter; 4096 of them page on 8 GiB and one run
took 2.5× another (§7). Irrelevant to the owner's bound (24 fighters = 12 MB) and listed only so the
pure-fighter curve is not misread.

**G6 — the eight.** `kMax*Contacts = 8`, first-come, nothing displaced (§11). Raising it costs memory per
unit and makes G2 worse in proportion. No measurement here resolves it; it is an argument FOR the "few
dozen modules" bound rather than a defect to fix.

**G7 — `FBBufferedLogSink` allocates on the hot path.** Every log line inside the parallel STEP builds
two `std::string`s and a `std::vector<FBLogField>` (`clients/FBLogSinks.h:53`); one `sensors` N = 2048
run emits 75 579 lines. A plausible part of the measured sequential fraction. Not isolated, not claimed.

**Measured and rejected as explanations:**

- *"The quadratic in the registry readers is what kills a mixed cast."* **Refuted.** 11.4 µs per cheap
  actor per sim-second against 24 observers — 6 % of that actor's own cost, ~1.3 % of the mixed cast
  (§4). A kind pre-sort is right and is not the lever.
- *"The walkers only look cheap because the cast is spread out."* **Refuted.** The same N = 512 `sensors`
  cast at 0.02° lattice pitch (extent ≈ 24 × 35 km) and at 0.002° (≈ 2.4 × 3.5 km, every actor inside
  every gate) cost 2148 µs and 2037 µs per actor per sim-second — the dense case is *cheaper*, within
  noise. Density does not drive it, because the per-pair work is the 928-byte copy plus the geometry,
  which runs whether the peer is in range or not, while the *detection* work is itself capped by the
  eight-slot tables. The 0.70 µs/peer coefficient is not a floor to be inflated for dense fights.
- *"Threading fixes it."* No — and for the cheap class threading does **nothing at all** (S(4) = 0.99 for
  inert targets, §8), because none of its cost is in the parallel STEP.
- *"A missile is a cheap actor."* No: ~1050 µs, two thirds of a fighter with its boxes off (§2).
- *"A ground position is a cheap actor."* Only below N ≈ 500. Above that its four walkers make it cost
  more than a fighter's airframe does (§2, §5).

## Knowledge

### 1. The three traps, and why the answer is "index the looking, never the actor"

**Trap 1 — determinism.** CLAUDE.md principle 4: if the pace decides the result, the coupling is
non-deterministic, and that is a bug. An actor computed differently because it is far from something is
exactly that. The rule that survives: *an elision is admissible only if it is provably RESULT-IDENTICAL,
or if it follows from the simulation itself.* A radar gate and a radio horizon are the second kind — they
are physics and they are already in the tree (§10). "Skip the far ones because skipping is cheap" is the
first kind, and §9's fingerprint is the instrument that decides it: run the same cast at
`--threads 1/2/4` before and after; the SHA-256 must not move.

**Trap 2 — the perception boundary.** "Out of range" is a SENSOR statement. FlightBox has no world-level
range and must not acquire one: the registry is anonymous by decision (`doc/sensors.md`), a contact
carries no identity, and **a gym run has no player at all**. Any index must be keyed on the looking
sensor's own gate — per walker, per mode — never on a distance to a privileged actor. A "distance to the
camera" would be a world rule derived from a camera position: the same class of error as letting the AI
read the registry.

**Trap 3 — the judges.** `core/FBFlightMonitor` and `core/FBMissionMonitor` judge every unit every tick,
and every client running a sim loop must feed both. A dormant unit that is still judged is a
contradiction; a dormant unit that is not judged is an unjudged actor. **So dormancy cannot be a runner
decision at all.** The shape that survives all three: *the actor is always stepped in full and always
judged; only the LOOKING is filtered, and only by something the looking sensor could itself justify.*

Candidates, costed against what was measured:

| candidate | what it removes | cost | determinism | measured prize |
|---|---|---|---|---|
| **A. Kind/emission pre-sort in `FBRwrSystem`** — test the published emission (a `bool Radiating` on `FBUnit`, or the existing `Mode == None`) BEFORE the 928-byte copy and the geodesy | the only reader that pays full price for a cheap actor | ~10 lines, one published bit | **safe: result-identical by construction** — the units it skips are exactly the ones the loop already rejects further down | 1.3 % of the mixed cast, up to 30 % of a 1024-fighter cast |
| **B. Telemetry that is not 184 columns per actor per tick** — a per-unit sample rate, `telemetry off` as a `.fbm` key, or a binary column store | ~94 % of a cheap actor's cost; 143 GB per sim-hour at 4096 actors | a `.fbm` keyword and a sink | safe: the fingerprint compares runs to runs, and every run decimates identically | up to 4096 × ~180 µs = 0.74 s per sim-second at the top end |
| **C. Spatial index over the published poses** — a uniform cell grid rebuilt once per tick at the `PublishPose` barrier, O(N) counting sort into buckets preallocated to `maxActors`; each walker queries only the cells its gate intersects | the 0.70 µs·N term, down to 0.70 µs·k | one O(N) build per tick, ~8 B/actor; every walker's loop HEAD changes, the BODY does not | **safe iff the query returns peers in REGISTRATION order** — the eight-slot tables are first-come and displace nothing (§11), so a different visit order changes which eight a unit holds. ### 2. Recommendation, aimed at the cheap class

1. **Do nothing about compute yet.** Two dozen modules plus a thousand positions and a thousand targets
   run at ~real time in 194 MB (§3). The measured limit is not the CPU.
2. **Build B (telemetry).** It is 94 % of the cheap class's cost and 100 % of its disk problem, it is
   result-preserving, and it is a `.fbm` keyword plus a sink. Isolate the 180 µs first (G1) so the
   split between the formatter and `PublishPose` is known before either is optimised.
3. **Build A (the RWR pre-sort).** Ten lines, provably result-identical, and it removes the ONE
   quadratic that runs over actors that could never be seen. Small in the mixture, large in a
   fighter-heavy cast — and it is the correct shape regardless of size.
4. **Do not build C yet, and never build D.** C's prize is ~0 for the mixture the owner described and
   large only for hundreds of mutually looking actors — which the "few dozen modules" bound rules out.
   D fails determinism, the perception boundary and the judges at once.
5. **Fix G4 (the file-descriptor cap) before anyone runs a thousand-actor cast on another host**, and
   close G3 (the store-fuze pass) with a cast that actually shoots — it is the one place a mixed
   theatre could still surprise.
